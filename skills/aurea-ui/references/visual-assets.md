# Visual Assets and Deliverable Routing

Use for hero imagery, illustrations, product visuals, icons, image mockups, and reference-led asset edits. Follow the host's available image tools and their requirements.

## Deliver the requested medium

| Intended result | Route |
| --- | --- |
| Working website, interaction, application source | Implement software; image assets support it |
| Image mockup or visual exploration | Produce a concept image if generation is available; label it as nonfunctional |
| Editable, exact typography or reproducible layout | Use appropriate layout/vector/code tools, preserving requested source files |
| Quantitative chart | Render from real data with deterministic axes, units, labels, and scales |
| Structured flow, architecture, or dependency diagram | Use structured diagram source and verify relationships |
| Illustration, photography-like visual, creative image edit | Use suitable image generation/editing tools or authorized existing assets |

Interpret ambiguous requests using the surrounding task. Clarify only when the choice between an image and working software materially changes the deliverable. Do not satisfy a request for a functioning interface with a screenshot.

## Asset brief

Before making or selecting an asset, identify its job and place in the design:

- Purpose and audience; what the asset explains, demonstrates, or communicates.
- Placement, aspect ratio, responsive sizes, subject focal point, and text-safe space.
- Brand palette, illustration/photographic style, material, lighting, and perspective.
- Required words, names, numbers, language, or an explicit absence of embedded text.
- Background/transparency, crop constraints, and source/usage rights where relevant.
- For edits: the exact target change and the identity, product features, or regions to preserve.

Example: “Hero illustration for a Vietnamese budgeting app: calm geometric style, warm neutral palette, 4:3 canvas, subject concentrated right, left area quiet for live HTML copy; mobile crop must retain the main subject; no embedded UI labels.”

## Integrate with the interface

For a working website, keep navigation, headings, CTAs, and essential information as semantic live text/controls rather than baking them into decorative imagery. A visual mockup may render text as part of the image, but must be labeled accordingly.

Use consistent identity, palette, lighting, geometry, and perspective across an asset set. Preserve product shape and markings in reference edits. Crop according to a defined focal point; use a separate mobile composition when one crop cannot preserve meaning. Verify alpha transparency when requested.

Follow project conventions for asset storage. Select local files, an existing asset pipeline, or approved storage/CDN based on the deployment; no provider or upload command is universally required. Reserve dimensions, choose appropriate image formats and sizes, and avoid unnecessary downloads for hidden/below-fold media. Do not lazy-load a critical hero asset without considering its loading role.

## Verify and report

Inspect assets at their actual desktop and mobile placement. Verify requested wording and critical numbers, subject completeness, crop, contrast with overlaid live text, and continuity with the design system. Inspect relevant details more closely when a visible defect or exactness requirement warrants it.

Describe informative imagery with contextual alternative text; mark purely decorative imagery appropriately. Do not invent product screenshots, client logos, testimonials, or usage rights as proof of a real product.

If generation is unavailable, use supplied/permitted assets or deliver an actionable asset brief and identify the missing output. A placeholder is not a completed generated image. Deliver editable sources or individual asset files when requested, and report remaining critical defects without endless subjective regeneration.
